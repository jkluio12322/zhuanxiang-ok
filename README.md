# BlueCar STM32F103 循迹小车

本工程基于 STM32F103ZET6 和 STM32 HAL，实现八路数字循迹、双轮速度闭环、
OLED 状态显示和 VOFA+ 遥测。

本文只记录**当前源码能够确认**的参数和控制思路。硬件参数以实测使用的
JGB37-520 12V、178 RPM、1:56 减速版本和 11 PPR 编码器为准。

> 本文与代码冲突时，**以代码为准**。改动行为后请同步更新本文。

> 想先一页看懂整体（能干什么、时序模型、三个模式、算法要点、接口一览），
> 看 [功能概览.md](功能概览.md)；本文负责参数与细节。

## 3. 电机与编码器参数

| 参数 | 数值 |
| --- | --- |
| 减速比 | 1:56 |
| 空载转速 | 178 RPM |
| 额定转速 | 140 RPM |
| 额定转矩 | 6.5 kg·cm |
| 堵转电流 | 2.3 A |

输出轴每转计数：

```text
counts_per_output_revolution = 4 * 56 * 11 = 2464
```

50 ms 控制周期的转速换算为：

```text
RPM = count * 1200 / 2464
RPM = count * 0.487012987
count = RPM * 2.053333
```

车轮半径为 `0.065 m`，轮胎周长约 `0.408407 m`。

## 4. 控制架构

代码按职责分层，依赖只能向下：

```
Display / Comm  ->  State  ->  Control / Motion  ->  Scheduler  ->  Hardware
```

| 目录 | 模块 |
| --- | --- |
| `Config/` | `app_config.h`（全部可调参数）、`app_types.h`、`board.h`（引脚别名） |
| `Scheduler/` | `app_scheduler`（中断分发、延后任务、ConfirmCounter） |
| `State/` | `app_state`（唯一可变状态）、`app_imu`（MPU6050 采样） |
| `Motion/` | `app_motion`（编码器、滤波、电机输出）、`app_speedloop`（50 ms 控制） |
| `Control/` | `app_pid`、`app_tracking`（循迹）、`app_testmode`（开环测试） |
| `Comm/` | `app_serial`、`app_console`（命令行）、`app_cmd`（按键与命令队列）、`app_telemetry` |
| `Display/` | `app_display` |

### 4.1 任务与执行位置

TIM5 提供 1 ms 时间戳；TIM6 每秒触发 1000 次，由 `app_scheduler.c` 分频。

| 周期 | 任务 | 执行位置 |
| --- | --- | --- |
| 10 ms | MPU6050 采样与姿态解算 | **TIM6 中断内** |
| 20 ms | 按键状态机 + 按键转命令 | **TIM6 中断内** |
| 20 ms | 循迹（或 PWM 循迹测试） | **TIM6 中断内** |
| 50 ms | 编码器测速、速度环、命令执行、遥测快照 | **TIM6 中断内** |
| 50 ms | 遥测格式化与发送 | 主循环（延后） |
| 100 ms | OLED 状态页刷新 | 主循环（延后） |
| 主循环 | 串口命令行解析与响应、OLED 缓冲写入 | 主循环 |

**为什么这样分**：USART1 一个字节只要 86.8 µs，而遥测 `snprintf` 16 个浮点要
100–300 µs、OLED 的 I2C 刷屏可能上 ms。把它们放进最高优先级中断会压住串口
接收导致丢字节。而速度环和循迹环按**固定周期常数**（50 ms、`dt = 0.02`）
计算，挪到主循环产生抖动就会算错，所以必须留在中断里。

主循环只有：`AppDeferred_Run()`（跑延后任务）+ 串口命令行 + `OLED_Flush()`。

中断在 `AppScheduler_Init()` 之前不放行任何任务，避免改到还没初始化的对象。

### 4.2 命令队列

按键产生的启停、模式切换、换档命令写入 8 项环形命令队列，由 50 ms 控制任务
集中执行；队列满时丢弃新命令，不覆盖尚未执行的控制动作。

USART1 命令行**同样没有绕开队列的路径**：`l`/`r`/`t`/`stop`/`quiet`/`log` 都写入
同一个队列，由 50 ms 控制任务统一执行，`show` 只读。命令行因此不会和中断里的
速度环抢同一份状态——`l 30` 在主循环解析，而轮速目标被 50 ms 控制任务读写，
直接改就是一处竞争。

在线改 PID 参数的路径已经删除：参数只在 `app_config.h` 的定义处改，改完重新
编译烧录，因此不存在"运行时改了、掉电就丢"的临时状态。

### 4.3 八路数字循迹

#### 4.3.1 传感器与误差

循迹模块是**八路数字量红外**（`irtrack.c` 用 `HAL_GPIO_ReadPin` 读，没有 ADC），
所以只有开关量信息，没有亚传感器分辨率。

驱动层把八路归一化成：`raw = 0` 表示压黑，`raw = 1` 表示白线；`pattern` 的
bit0–bit7 对应 IR1–IR8，压黑置 1。通道权重按物理间距设定：

```text
-25, -17, -9, -3, +3, +9, +17, +25
```

并算出**归一化质心**：

```text
e_y = (权重和 / 压黑通道数) * 0.28
```

`e_y` 的范围约为 ±7，**与压了几路无关**——这是这套算法的关键：旧版本直接把
未归一化的权重和当误差，压 1 路最大 ±25、压 5 路能到 ±65，同一个增益要面对
2.6 倍的量纲漂移，只能靠一堆降速和限幅去补。

单路压黑时 `e_y` 只有 8 个可能取值，这是数字量传感器固有的：

| 压黑通道 | IR1 | IR2 | IR3 | IR4 | IR5 | IR6 | IR7 | IR8 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `e_y` | −7.00 | −4.76 | −2.52 | −0.84 | +0.84 | +2.52 | +4.76 | +7.00 |

#### 4.3.2 线路有效性

有效线路 = **压黑 1–7 路且连成一段**。另外两种图案判为无效：

- 八路全黑（`TRACK_LINE_VALID_MAX_BLACK = 7U`）
- 断续图案（例如 IR1 和 IR8 都黑、中间全白）——数字量传感器很容易出这种图案
  （斜穿横线、岔路口），不判无效的话质心会算出个"居中"的假象

#### 4.3.3 控制链：级联双环

```text
档位速度 base_rpm
    │
    │   循迹环（位置式 PD，20 ms）
    │   e_y ──> PID ──> steer_rpm（差速，限幅 ±60）
    │
    ├──> 左目标 = base + steer ──> 左速度环（增量式 PI，50 ms）──> 左轮 PWM
    └──> 右目标 = base − steer ──> 右速度环（增量式 PI，50 ms）──> 右轮 PWM
```

**循迹环只出目标转速，不直接碰 PWM。** 真正的电机输出由左右两个速度环闭环
给出，所以差速也是闭环的：某个轮子跟不上目标（静摩擦、地面阻力）时，它自己的
速度环会把 PWM 顶上去补，而不是等平均环慢慢纠。

| 环 | 形式 | 默认参数 |
| --- | --- | --- |
| 循迹环 | 位置式 **PD**（无积分） | `Kp = 4.3`、`Ki = 0`、`Kd = 0.7`、输出限幅 ±60 RPM |
| 速度环 | 增量式 **PI**（无微分） | `Kp = 0.25`、`Ki = 0.020`、`Kd = 0`、输出 ±100% |

位置环不给积分：线就在那儿，跟着走就没有稳态误差，加 I 只会在出弯积一堆造成
超调。速度环不给微分：测速有噪声，微分会把它放大成抖动。

**速度环的核心作用不只是调速，而是抗电池掉压**：电池从 12V 掉到 10V，同样的
PWM 转速会掉约 15%，只有闭环才能让"G3 = 80 RPM"始终成立。

循迹模式下左右速度环的输出下限收到 0（不允许轮子反转），**由 PID 自己限幅**
而不是在外面把负数改成 0——增量式 PID 的"积分"就是输出本身，外部改成 0 会让
内部输出停在 −100，出弯要一路爬回来。手动模式下恢复 −100…+100（原地转需要
一正一反转）。

#### 4.3.4 计圈

不用状态机，直接数 **`e_y` 偏到一侧**的事件：

- **弯道**：转弯时黑线偏到一侧，`|e_y|` 很大；
- **起点横线**：压满八路时是对称的，权重和 `-25-17-9-3+3+9+17+25 = 0`，
  所以 **`e_y ≈ 0`**。

判据是 `|e_y| >= 3.0` **连续 3 个 20 ms 周期**（60 ms），计一个弯；
计完后 10 个周期（200 ms）内不再接受新弯。累计 4 个弯计一圈。

**为什么用持续时间区分而不是幅度**：斜穿起点横线时某一瞬间可能只压住一侧，
例如 IR1–IR4 压黑时 `e_y = -3.78`，超过阈值。但横线是**一闪而过**的——按
100 RPM、轮径 0.065m 算车速约 0.68 m/s，20mm 宽的横线约 30 ms 通过，只有
1.5 个周期；而转弯持续几十到几百毫秒。所以 3 个周期的确认窗口能把横线滤掉、
同时抓住弯道。

实车若发现横线仍被误计，把确认周期加到 4~5；若弯道漏计，减小阈值。

> **适用面**：这套计圈假设赛道是「四个直角弯 + 一条起点横线」的矩形。
> 换成 S 弯或连续弯需要重新设计。

#### 4.3.5 状态机

只有四个状态：

| 状态 | 进入条件 | 行为 |
| --- | --- | --- |
| `ACQUIRE` | 启动 | 直行 50 个周期（1 秒）后转入 FOLLOW |
| `FOLLOW` | 正常 | 循迹环出转向；`e_y` 偏到一侧累计计圈 |
| `LOST` | 线路连续 3 周期无效 | **保持丢线前的舵量**，不做任何计算 |
| `STOPPED` | 停车 | — |

停车条件：八路全白连续 50 个周期（1 秒）；或丢线连续 100 个周期（2 秒）。

### 4.4 开环测试模式

| 模式 | 行为 |
| --- | --- |
| PWM 速度测试 | 左右轮同向同速按当前档位跑，默认每 5 秒换一次转向 |
| PWM 循迹测试 | 固定基础占空比加减差速；误差来自注入的**八路图案**，不读真实红外 |

PWM 循迹测试**复用循迹环的同一个 PID**，所以测试和实战的转向特性一致。

**PWM 循迹测试的模拟输入是原始传感器图案，不是一个抽象的角度。** 固件把 8 位图案
直接写进驱动层的 `ir_data.raw[]`，当成八路传感器的读数，再走与实车**逐字相同**的
计算链：驱动层算归一化质心（`e_y`，公式见 §4.3.1）→ 循迹模块判线路合法性 →
同一个 PID 算差速。所以误差的量纲天然和实车一致，没有任何手工标定的映射系数。

图案表共 12 项（`app_testmode.c` 的 `patternTable[]`），按 IR1→IR8 从左到右写，
`1` = 压黑：

| 图案 | 场景 | `e_y` |
| --- | --- | --- |
| `11000000`、`01100000`、`00110000` | 直线上的普通偏移（左，2 路连续压黑） | −5.88 / −3.64 / −1.68 |
| `00011000` | 居中（IR4+IR5） | 0.00 |
| `00001100`、`00000110`、`00000011` | 直线上的普通偏移（右） | +1.68 / +3.64 / +5.88 |
| `11110000`、`00001111` | 转弯口（4 路连续压黑） | −3.78 / +3.78 |
| `11111111` | 全黑 = **丢线** | 无效 |
| `00000000` | 全白 = **到终点线** | 无效 |
| `10000001` | 岔路口（中间断开） | 无效 |

两种无效图案走的是实车那两个守卫：`11111111` 压满 8 路、超过
`TRACK_LINE_VALID_MAX_BLACK`（7）按横线处理；`10000001` 中间有白洞被
`line_is_contiguous()` 挡下。**丢线与全白的处理也和实车共用同一份判定、确认计数和
停车规则**：连续 3 个周期无效判丢线并保持丢线前的差速，丢线满 100 个周期（2 秒）
按丢线超时停车；八路全白满 50 个周期（1 秒）停车。注意「保持差速」的前提是已经有
差速——先用偏移图案把车跑起来再切全黑，才看得到保持效果。

按键：KEY2 按表中顺序轮换图案，KEY4 短按/长按调基础占空比。每 5 秒
（`PWM_TRACK_TEST_PHASE_MS`）会把**当前图案左右镜像**一次，所以停在任一非对称图案
上就能看到左右自动对调；镜像不改 KEY2 选中的那一项，表本身对镜像封闭。开机默认是
居中的 `00011000`，它是自对称的，所以开机状态下看不到自动镜像的效果。

OLED 的 PWM-TRK 页：

```text
[PWM-TRK] RUN        第 1 行：模式与运行状态
P:00011000 PH:LEFT   第 2 行：当前注入的图案（IR1→IR8，1 = 压黑）+ 相位
BASE:50% ERR:+00.0   第 3 行：基础占空比 + 循迹环算出的 e_y
```

第二行的 `PH:` 就是上面说的那个镜像相位：`LEFT` 表示注入的是 KEY2 选中的原图案，
`RIGHT` 表示注入的是它的左右镜像。

> **OLED 一行能放多少字符**：小字是 6×8 点阵，`128 / 6` = **21 个**；驱动的
> `OLED_ShowStringSmall()` 到 `col + 5 >= 128` 就停止写入，**超出的部分被静默丢弃**。
> 别把 `OLED_TEXT_BUFFER_SIZE = 24` 当成显示上限——那只是 `snprintf` 的缓冲区大小
> （23 字符 + 结尾符），两者不是一回事。本页最长的一行 `P:00000000 PH:RIGHT` 是 20 个字符。

**PWM 速度测试的转向控制权。** 默认 5 秒自动来回换向；也可以用串口 `l`/`r`/`t`
手动指定单轮转速（见 §7）。发这类命令会调用 `AppTestMode_SetAutoPhase(0)` 关掉
自动换向，`stop` 或切换模式时经 `AppSpeedLoop_ResetModeState()` 自动恢复。台架
测单轮正反转就用 `l 30` / `l -30`。

## 6. 通信

USART1 使用 PA9/PA10、115200 bps、8N1：

- TX 走环形缓冲区，`HAL_UART_Transmit_IT` 完成后自动接力。
- RX 用单字节中断接收，中断里只缓存字节转交命令行模块，不解析。
- `HAL_UART_RxCpltCallback` / `HAL_UART_TxCpltCallback` 定义在 `app_serial.c`。

USART2 的 CubeMX 初始化保留在 `usart.c`，但**应用未使用**（早期版本的蓝牙
手动控制链路已删除）。

## 7. 串口命令

命令通过 USART1 输入，以回车或换行结束。**本工程没有在线调参命令**——PID 参数
在 `app_config.h` 里改，重新编译烧录；串口只负责看数据和台架手动转轮。

| 命令 | 作用 |
| --- | --- |
| `l <rpm>` | 左轮目标转速，负值反转 |
| `r <rpm>` | 右轮目标转速，负值反转 |
| `t <rpm>` | 左右轮同时设为该值 |
| `stop` | 立即停车（并恢复自动换向） |
| `show` | 打印模式/相位/档位/基础占空比/左右目标与实际转速/三组 PID（循迹组附差速增益 `tkg`） |
| `quiet`、`log` | 暂停 / 恢复 VOFA 输出 |
| `help` 或 `?` | 显示命令列表 |

`l`/`r`/`t` **只在 PWM-SPEED 模式下生效**（用 KEY1 切过去）。其它模式下轮速目标
另有来源（循迹环、测试相位），改了下一个周期就被覆盖，所以命令行会直接回复
`[MANUAL] only in PWM-SPEED mode`，而不是入队后静默失效。

参数是**严格解析**的：整串必须就是一个数，范围是 ±190（`SPEED_TARGET_LIMIT_RPM`）。
所以 `l abc`、`l 30x`、`l 500`、`l nan` 都会被拒绝并给出提示，**不会入队、也不会把车
置成运行态**；成功时才回显 `[MANUAL] l 30.0 rpm`，队列满时回 `[MANUAL] queue full, dropped`。
（早先没有这道校验：`l abc` 会被 `strtof` 解析成 0 一路送进队列，顺带把车置成运行态。）

这三条命令**走命令队列**：主循环解析、50 ms 控制任务执行，避免和速度环抢状态。
执行时还会关掉 PWM-SPEED 的 5 秒自动换向，把转向控制权交给命令；`stop` 或切换
模式时经 `AppSpeedLoop_ResetModeState()` 自动恢复。

命令名不认识回复 `? '<名字>' (type 'help')`，缺参数回复 `? <名字> needs a value`。

`show` 的 `Tgt` 打的是**夹取后**的目标（取自速度环里存的值），所以 `t 500` 不会出现——
它已经在解析处被范围校验挡掉了；而如果下游有别的地方给出超限目标，`show` 显示的也是
车实际执行的那个值。

## 8. VOFA+ 遥测

控制任务每 50 ms 更新一次快照，主循环发送 16 个逗号分隔字段：

```text
tgtRpmL,rpmFL,voltL,tgtRpmR,rpmFR,voltR,steerRpm,diffRpm,yawDeg,trackError,mode,run,gear,turnPhase,rpmL,rpmR
```

| 字段 | 单位 | 含义 |
| --- | --- | --- |
| `tgtRpmL` / `tgtRpmR` | RPM | 左右轮目标速度 |
| `rpmFL` / `rpmFR` | RPM | 滤波后速度（中值-3） |
| `voltL` / `voltR` | V | 最终命令电压（PWM 百分比换算） |
| `steerRpm` | RPM | 循迹差速量 |
| `diffRpm` | RPM | 左右实际速度差 |
| `yawDeg` | 度 | MPU6050 航向角（**仅显示，不参与控制**） |
| `trackError` | — | 当前 `e_y`，范围约 ±7 |
| `mode` / `run` / `gear` | 枚举 | 工作模式 / 运行标志 / 档位 |
| `turnPhase` | 枚举 | 循迹状态机状态（原为"转弯阶段"，语义已变） |
| `rpmL` / `rpmR` | RPM | 原始速度，未滤波 |

表头由 `AppTelemetry_BootHeader()` 统一发出，不要在别处硬编码。

## 9. 构建与调试

### 9.1 Keil MDK

用 Keil MDK-ARM 打开 `MDK-ARM/bluecar.uvprojx`，目标 `bluecar`，器件
`STM32F103ZE`。命令行构建：

```powershell
UV4.exe -r MDK-ARM\bluecar.uvprojx -j0 -o build.log
```

### 9.2 VSCode + EIDE

用 VSCode 的 EIDE 插件打开 `MDK-ARM/` 目录（读 `.eide/eide.yml`），
使用同样的 ARMCC 5.06 工具链。

**增删或改名任何源文件时，`bluecar.uvprojx` 和 `.eide/eide.yml` 两个文件都要
同步修改**，包括 `IncludePath` 列表。

### 9.3 主机侧仿真

```powershell
python tools\simulate_tracking.py     # 八路循迹算法
python tools\simulate_pwm_tests.py    # PWM 测试模式算术
```

两个脚本都直接解析 `Core/Application/Config/app_config.h`，改宏后重跑即可验证，
不需要重新编译固件。**因此该文件里的宏必须是单行的 `#define 名字 数值`**。

### 9.4 串口调试

1. 将 USART1 的 PA9/PA10 接到 USB 串口工具，115200 bps、8N1。
2. 复位后可看到 `BOOT OK` 和 VOFA CSV 表头。
3. 使用 `help` 查看命令，使用 `show` 查看实时闭环状态。

### 9.5 实车调参

PID 参数都在 `app_config.h` 的定义处改，改完重新编译烧录（没有在线调参命令）。
**必须按这个顺序**，否则两个环会互相激发振荡：

1. **先整定左右速度环**。架空车轮，发 `t 30` 看左右轮是否都能稳到 30 RPM、
   不振荡；要分别看单轮就用 `l 30` / `r 30`（见 §7，只在 PWM-SPEED 模式下有效）。
   增益是 `SPEED_PID_KP` / `SPEED_PID_KI`，`SPEED_PID_KD` 默认 0。
2. **确认内环稳了再合上循迹环**，调 `TRACK_PID_KP`。低速下能把车拉回线上、
   不振荡即可。
3. **最后加 `TRACK_PID_KD`**。`e_y` 是阶梯量化值，`Kd` 放大的是量化台阶，
   宁小勿大；出现抖动就减。
4. 起步打顿时，再考虑给速度环加一点 `OutOffset`（`SPEED_PID_OUT_OFFSET_PERCENT`，
   默认 0）。
